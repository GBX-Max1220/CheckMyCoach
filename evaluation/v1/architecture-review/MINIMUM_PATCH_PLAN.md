### PATCH-2: Add Generic Correction Baseline

**File:** `evaluation/v1/baseline_correction.py` (new)

**What:** Implement the second condition (generic correction baseline). For each failure family, a deterministic rule:

| Family | Baseline Rule |
|---------|--------------|
| `unsupported_numerical_specificity` | Prepend `"Note: These values are approximate and may vary by individual."` then strip numerical patterns `\d+\.\d+` → `"varying"` |
| `unsupported_factual_claim` | Prepend `"Note: This claim may not apply to all individuals."` then wrap in `"Some research suggests..."` |
| `missing_safety_boundary` | Prepend `"Important: Consult a qualified professional before following this advice. Individual results and safety considerations vary."` |

No LLM calls. Pure string operations. Deterministic.

**Files touched:** 1 new file.

**Estimated effort:** ~60 lines.

**Depends on:** PATCH-1.

### PATCH-3: Add Validation Checks for Evaluation v1

**File:** `evaluation/v1/validation.py` (new)

**What:** Add four semantic validation checks that the existing M4 does not implement:

1. **`target_failure_removed`**: For NUM family, check that the specific numeric pattern no longer appears in the corrected text. For FCT family, check that the assertion strength (superiority word count) is reduced. For SAF family, check that a safety qualifier was added.
2. **`supported_information_retained`**: Character overlap ratio check (already in M4) + NER overlap (basic noun phrase retention — simple set intersection of extracted nouns).
3. **`new_unsupported_claims`**: Scan corrected text for new numeric claims or new superiority patterns that weren't in the original.
4. **`boundary_preserved`**: For SAF, check that condition/safety boundaries weren't removed.

Use regex patterns from `ucs_engine.py` Stage 1 patterns (already exist, reuse).

**Files touched:** 1 new file.

**Estimated effort:** ~150 lines.

**Depends on:** PATCH-1.

### PATCH-5: Generate 40 Evaluation Cases

**File:** `evaluation/v1/cases/` (40 new JSON files)

**What:** Create the 40 evaluation cases (15 NUM, 15 FCT, 10 SAF) as structured JSON files. Each case contains:
- Question text (formulated to trigger the target failure family)
- Input answer (generated by DeepSeek Chat, with the target failure present)
- Target span identifying the failure region
- Ground-truth evidence ceiling annotation (which evidence exists / doesn't exist for this question)

Case generation approach:
1. Write question prompts designed to elicit each failure type
2. Call LLM once per case to get the `input_answer`
3. Manually annotate the `target_span` and evidence ceiling
4. Store as `evaluation/v1/cases/{FAM}-{NNN}.json`

**Files touched:** 40 new case files.

**Estimated effort:** ~2-3 hours for question drafting + LLM generation + manual annotation.

**Depends on:** PATCH-1 (schema defined so cases match the format).
